WHY I USE DLT OVER AIRBYTE AS A DATA ENGINEER

2026-09-06
SUMMARY

Airbyte holds up for the demo. It struggles once pipelines get real: internal APIs with drifting schemas, nested-loop endpoints, anything custom — and debugging turns painful fast.

Since most teams run an orchestrator like Dagster or Airflow anyway, dlt lets ingestion live there too: one codebase, one place for logs, easy onboarding, nothing extra to self-host.

Airbyte still wins in one case: well-known third-party sources only, and no Python-literate team.

WHERE AIRBYTE STARTS TO HURT

Airbyte works great in the demo. It's the second month, once real pipelines show up, where the cracks show:

  • Logs that don't help you. When a sync fails, the logs are often vague enough that debugging turns into guesswork rather than reading a stack trace.
  • Internal APIs with schema drift. Third-party APIs are stable and well-documented. Internal ones change shape whenever another team ships something, and that's exactly where Airbyte's connector model gets brittle.
  • Nested-loop and custom pipelines. The moment you need to paginate through a list endpoint, then call a detail endpoint per item, then paginate that, you're fighting the low-code builder instead of writing the three lines of Python that would have solved it directly.
  • Self-hosting. It works, until it doesn't, and when it doesn't you're now debugging Airbyte's own infrastructure on top of your pipeline.

WHY DLT WINS ONCE YOU HAVE ORCHESTRATION ANYWAY

Here's the thing almost every team running Airbyte already has: Dagster or Airflow, because ingestion alone was never going to cover transformation, scheduling, and dependencies. If an orchestrator is already in the stack, ingestion may as well live there too — and that's exactly what dlt is built for. A resource is just a Python generator: 

import dlt

@dlt.resource(write_disposition="merge", primary_key="id")
def orders(updated_at=dlt.sources.incremental("updated_at")):
    for page in fetch_orders_since(updated_at.last_value):
        yield page

pipeline = dlt.pipeline(
    pipeline_name="internal_orders",
    destination="snowflake",
    dataset_name="raw_orders",
)
pipeline.run(orders())

The nested-loop case that breaks a low-code builder is just a nested generator here: 

@dlt.resource
def order_line_items():
    for order in fetch_orders():
        for item in fetch_line_items(order["id"]):
            yield {**item, "order_id": order["id"]}

And schema drift on an internal API isn't a config screen you hope handles it — dlt evolves the destination schema automatically as new fields show up, and you can set a contract when you want drift to fail loudly instead of silently: 

@dlt.resource(schema_contract={"columns": "evolve", "data_type": "freeze"})
def orders():
    ...

Past the mechanics, the bigger win is organizational: pipelines, transformations, and orchestration all live in one repo, in one language, under one version control history. Logs are whatever your orchestrator already surfaces, not a second system to learn. Onboarding a new data engineer means reading Python they already know, not learning a separate platform's quirks and self-hosting setup on top of it. Validation is just code — assert what you need, log what you want, exactly where you need it. Backfills are a parameter, not a support ticket: 

pipeline.run(orders(updated_at=dlt.sources.incremental(
    "updated_at", initial_value="2024-01-01"
)))

THE CHERRY ON TOP

dlt even ships docs specifically for migrating off Airbyte, which tells you something about how common this move already is. And Airbyte's paid tier is, frankly, a lot of money for what you get once you've priced out what the equivalent custom pipeline costs in engineering time.

WHERE AIRBYTE IS STILL THE RIGHT CALL

None of this makes Airbyte bad, it makes it a fit for a narrower case than it's usually sold for: every source is a well-known third-party connector, nothing custom or internal, and the team has no Python-literate data engineers to maintain code-based pipelines. In that specific setup, the low-code trade-off is the right one.

Internal APIs / schema driftBrittleSchema evolves (or fails loudly, your choice)
Nested / custom pipelinesFighting the low-code builderA nested generator

TAKEAWAY

If you're already running Dagster or Airflow, and your sources are anything but a clean set of popular third-party APIs, dlt means one codebase instead of two, one place to debug instead of two, and one thing to onboard a new engineer onto instead of two. Airbyte isn't wrong — it's just solving a problem you may not actually have.
