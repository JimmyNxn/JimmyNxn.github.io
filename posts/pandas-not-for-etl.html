WHY PANDAS SHOULD NEVER BE IN YOUR ETL PIPELINE

2026-09-11
SUMMARY

I reach for pandas constantly. I just never reach for it inside a pipeline. Exploration, plotting, feeding a classic ML model — that is the job it was built for, and nothing else does that job better.

For validation, processing, and loading, I want pydantic and dlt. Pandas' great talent is carrying on regardless: wrong dtypes, exploded joins, misaligned indices, all without raising a finger. A pipeline is the one place where carrying on regardless is the bug.

WHERE PANDAS EARNS ITS KEEP

Credit first. For interactive work, nothing beats it. df.groupby(...).plot() in a notebook. Poking at an unfamiliar CSV until its shape makes sense. Handing a DataFrame straight to scikit-learn's fit(X, y). That loop — question, answer, next question — is what pandas was designed for, and it is superb at it. So this isn't an anti-pandas post. It's an anti-pandas-in-production post.

THE REAL PROBLEM: IT FAILS QUIETLY

A pipeline exists to stop bad data before it reaches a table somebody trusts. Pandas is built on the opposite instinct: keep going, infer something sensible, don't interrupt. In a notebook that's a kindness, because you can see the output. In a pipeline it's how a wrong number lands in a dashboard three joins later without leaving a single line in the logs.

Start with dtype coercion. One missing value, and an integer column turns into floats:

// python 
import pandas as pd

df = pd.DataFrame({"id": [1, 2, 3]})
df.loc[1, "id"] = None

print(df["id"].dtype)
# float64 — not int64, no warning, no error

Every downstream system expecting an integer primary key now gets 1.0 instead of 1. Most of them will find out the hard way.

Joins are worse. A duplicate key on one side quietly multiplies rows on the other — no error, no row-count assertion, just more data than you asked for:

// python 
merged = orders.merge(customers, on="customer_id")
# if customer_id isn't unique in `customers`, orders just got duplicated.
# merged.shape is bigger than orders.shape. nothing told you.

Neither of these raises. Neither turns anything red. You find out when finance asks why revenue is up 12% on last week.

THE REST OF WHY IT DOESN'T BELONG HERE

Dtypes and joins would be enough on their own. They aren't the only things working against it.

Everything goes into memory. There is no real streaming model: read_csv and its siblings materialize the entire frame before you can look at a single row. dlt treats data as an iterator instead — rows arrive, get validated, get written, and the full dataset never sits in RAM at once. When a source outgrows the machine, pandas doesn't degrade. It just stops.

"Missing" has four faces. NaN for floats, None for object columns, NaT for datetimes, pd.NA for the newer nullable dtypes — four spellings of nothing, each behaving a little differently in comparisons and boolean masks (NaN == NaN is False, to start with). Writing one check that answers "is this value missing?" consistently across a real frame's mixed dtypes becomes a small project of its own.

The API fights row-level logic. Validation is a row-at-a-time problem: look at this record, decide, reject it, say why. Pandas is column-oriented to its core, so that one if-statement turns into a wrestling match with chained indexing and the SettingWithCopyWarning it drags along.

And going row by row anyway doesn't rescue you:

// python 
for idx, row in df.iterrows():
    validate(row)
# iterrows() boxes every row into a fresh Series, discarding per-column
# dtypes in the process — on anything but a tiny frame, this is some
# of the slowest code you can write in pandas

Iterating plain dicts — or pydantic models — off a generator costs none of that. No boxing, no dtype loss, and it's the same code path production runs anyway.

WHERE VALIDATION BELONGS: PYDANTIC

A pipeline should fail loudly, at the boundary, the instant a row stops looking like what you promised — not nurse a NaN through five transform steps and hope. A typed model gives you exactly that:

// python 
from pydantic import BaseModel, ValidationError

class Order(BaseModel):
    id: int
    customer_id: int
    amount: float

try:
    order = Order(**row)
except ValidationError as e:
    logger.error(f"rejected row {row['id']}: {e}")
    continue

No silent coercion, no "close enough." The bad row gets caught, logged with a reason, and kept out of the table — at the point of failure, rather than three dashboards downstream.

WHERE LOADING BELONGS: DLT

Once a row is valid, loading it is a solved problem — just not one pandas ever set out to solve. to_sql() knows nothing about incremental loads, merge semantics, or schema evolution. dlt knows all three:

// python 
import dlt

@dlt.resource(write_disposition="merge", primary_key="id")
def orders(updated_at=dlt.sources.incremental("updated_at")):
    for row in fetch_orders_since(updated_at.last_value):
        yield Order(**row).model_dump()

pipeline = dlt.pipeline(destination="snowflake", dataset_name="raw_orders")
pipeline.run(orders())

Validate with pydantic, load with dlt, and pandas never touches a row it could quietly mangle.

PANDASPYDANTIC + DLT
Bad dataCoerces silently (NaN, dtype drift)Rejects loudly at the boundary
JoinsCan silently multiply rowsExplicit, typed, no surprise fan-out
Missing valuesNaN / None / NaT / pd.NA, each behaving differentlyOne concept: the field is missing or it isn't
MemoryWhole dataset materialized upfrontStreams row by row
Row-level logiciterrows() — slow, boxes every rowPlain dicts/models, no boxing
SchemaWhatever the data happens to beDeclared, enforced, versioned
Loadingto_sql(), no incremental/merge logicIncremental, merge, schema evolution built in
Best fitExploration, plotting, classic MLValidation, processing, production loads

TAKEAWAY

Pandas is a scientist's tool: fast, flexible, forgiving. A pipeline needs the opposite of forgiving — it needs to stop dead the moment something is wrong. So keep pandas in the notebook, where forgiving is the entire point. In the pipeline, let pydantic reject what shouldn't pass, and let dlt load what should.
