HOW TO MAKE YOUR DBT PROJECT'S CI EFFICIENT WITHOUT REDUCING TEST COVERAGE

2026-09-06
SUMMARY

--sample shrinks a dbt run to a recent time window, turning an expensive full-history CI job into pocket change. Great for your warehouse bill, terrible for freshness and relationship tests, which quietly start lying to you. The fix: keep sampled runs for fast PR feedback, and route the full, unsampled test suite through a separate orchestrated pipeline (here, Dagster) — then gate the actual release branch on that full run passing, not the sampled one.

THE PROBLEM

Slim CI (--select state:modified+) already cuts most of the waste out of dbt CI runs — you only build and test what changed plus its downstream blast radius, compared against a stored manifest from prod: 

dbt build --select "state:modified+" --state ./prod-manifest

Great in theory. In practice, "only the modified subgraph" can still mean rebuilding a fact table with three years of history because one column got renamed. Your PR touched one line of SQL. The warehouse did not care, and billed accordingly.

HOW --SAMPLE WORKS

This is where --sample earns its keep. Tell dbt a relative window and it quietly tacks on a time filter to any model with an event_time column configured — same SQL, same logic, a fraction of the bytes scanned: 

dbt build --select "state:modified+" --state ./prod-manifest --sample="3 days"

configured once per model, in the schema file:

models:
  - name: fct_orders
    config:
      event_time: order_created_at

On a warehouse that bills by bytes scanned, that's not a rounding error. A model that normally reads eighteen months of history to validate a one-line SQL change now reads three days of it, and the difference shows up on the invoice, not just the stopwatch:

Full history (18 months)~640 GB~$3.20 / run

(Ballpark numbers for a mid-size warehouse — yours will differ, but the shape of the curve won't: this scales with history, and history only grows.)

Which is the part where sampling starts sounding too good to be true. It is. Two test types find the catch immediately.

WHERE IT BREAKS: FRESHNESS TESTS

Freshness tests measure how recent your source data is — max loaded_at versus now. Sampling a downstream model doesn't make the source fresher or staler; the check is answering a question sampling has no opinion on. Best case it's a no-op that wastes a CI cycle: worst case, someone reads a green freshness check on a sampled run as "our data pipeline is current," and it was never testing that in the first place.

WHERE IT BREAKS: RELATIONSHIP TESTS

Relationship tests are the one that breaks quietly, and quietly is worse than loudly. Say fct_orders and dim_customers are both sampled independently to the same 3-day window: 

- name: fct_orders
  columns:
    - name: customer_id
      tests:
        - relationships:
            to: ref('dim_customers')
            field: customer_id

An order placed yesterday can reference a customer who signed up four months ago. The order is in the sample window. The customer isn't — their row's event_time falls well outside the last three days, so their sampled slice never includes it. The test fails. The data was never wrong. Multiply that across a real DAG and slim+sampled CI starts crying wolf often enough that people stop reading the alerts — which is the exact failure mode a test suite exists to prevent.

THE FIX: SPLIT FAST FROM FULL

The fix isn't "sample more carefully" — you can't out-clever a join across two independently truncated windows. The fix is admitting CI is being asked two different questions, and giving each one its own answer: 

PR pushed
  └─ CI: dbt build --select "state:modified+" --sample="3 days"
       (fast, cheap, answers: "does this SQL do what I think?")

merge to main
  └─ Dagster: full, unsampled run — freshness + relationships + everything
       (slow, thorough, answers: "is this actually safe to ship?")

release-please branch
  └─ merge gate: waits on the Dagster run for this commit, not on PR CI

PR CI stays sampled and fast — minutes, not an hour, on every push. The release-please branch doesn't take PR CI's word for it: its merge check listens for the Dagster pipeline tied to that exact commit to report success before it'll let the merge through. Green PR tests get you reviewed and mergeable to main. Green Dagster run is what actually unlocks a release. Nobody ships on a sampled run alone, and nobody's blocked on a full warehouse scan just to get feedback on a PR.
